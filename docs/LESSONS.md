# 经验教训

开发中真实踩过的坑，每条尽量写「现象 → 根因 → 修法 → 回归测试」。动手前必须记得的操作规则已提炼到 `CLAUDE.md`「开发注意」；这里是完整记录，按时间倒序（新的在前）。

- **拆大文件用 AST 切片脚本、别手搬**（admin.py 4000 行 → admin/ 包）：按 `ast` 找到顶层辅助函数与闭包内每条语句的行区间（含前导注释、装饰器），按路由前缀分模块、按「被哪些模块引用」自动决定辅助函数归属（只被一个模块用 → 跟它走，多个 → common），跨模块引用生成 import 并断言无环；闭包共享变量收进一个上下文对象，各模块 `mount(ctx)` 里用同名别名，路由体一字不改。证明「纯搬运」的办法：拆前后 path+methods 集合相等 + 全量测试 + 起两个实例对每条路由 curl 状态码对拍（0 差异）。两个坑：包内相对导入要加深一级（`from .x` → `from ..x`，函数体内的惰性导入也要）；`Path(__file__).parent` 这类相对路径随文件搬家而变。
- **全量 curl 对拍路由要给 `-m` 超时并跳过 SSE 端点**：`/admin/notifications/stream` 永不结束，循环卡在那里会被当成「命令跑不完」。
- **浏览器扩展的 click 偶尔不触发 inline `onclick`**（「新增连接」按钮按坐标/按 ref 点都没开弹窗），用 `javascript_tool` 直接 `el.click()` 即触发——先用 JS 复核再下「功能坏了」的结论。
- **看板图表的深色配色不能只把浅色值调暗**：琥珀（被挡下）与红（出错）在深色底上、红绿色弱视下 ΔE 只有 3.5，dataviz 校验器直接 FAIL；换成蓝才两套主题都过。「被挡下」本就是审批流的正常一步而非警告，蓝反而更准确。
- **包名是 `dbmcp`，不是 `dbm`**：`dbm` 是 Python 标准库模块，会被 stdlib 遮蔽导致 import 全挂。CLI 命令仍叫 `dbm`。
- **本机测本地服务要绕过代理**：这台机器 shell 有 SOCKS 代理环境变量，不绕过会把 127.0.0.1 请求发进代理得到 502。curl 用 `--noproxy '*'`；fastmcp Client（底层 httpx）用 `env NO_PROXY='*' no_proxy='*'`（单纯 `-u ALL_PROXY` 不够，httpx 还会读其他代理变量，NO_PROXY 最稳）。MCP 客户端同样：接入指南里要写 `NO_PROXY=127.0.0.1,localhost`。
- **MCP 接入指南别只写 Claude Code 一条命令**：各家配置格式不同——Codex 是 TOML `[mcp_servers.x]`（不是 JSON）；Cursor HTTP 的 `type` 必须 `"http"`（`"streamable-http"` 会让 `cursor-agent` 静默丢掉整份 `mcp.json`）；DeepSeek Harness 走 `cordis.yml` 的 `@deepseek-ai/dsh-mcp-client`，模型看到的工具名带 `mcp__<serverName>__` 前缀；Gemini CLI streamable HTTP 字段是 `httpUrl`（`url` 是旧 SSE）；Windsurf 远程端点字段是 `serverUrl`；Claude Desktop 的 `claude_desktop_config.json` 只认 stdio，HTTP 要走 Settings → Connectors，把 `url` 写进 JSON 会被整段抹掉。**推荐一律接常驻 HTTP `http://127.0.0.1:8100/mcp`**，不要给每个 agent 再起一份 `--stdio`（审批单对不上正在看的后台）。审批等待默认 120s，客户端默认超时常是 60s（Codex `tool_timeout_sec`、DeepSeek `toolCallTimeoutMs`）必须调到 ≥180s。完整配方在 README「接入 Agent」。
- **写 sqlglot 相关逻辑前先跑实验脚本验证解析行为**：已验证的坑——PG 方言 `EXPLAIN`/`SHOW` 退化为不透明 `Command` 节点需特判；`WITH x AS (INSERT ...) SELECT` 顶层是 `Select`，必须遍历整棵树找写节点。
- fastmcp 3.x 装的是 `fastmcp` + `fastmcp-slim`，其依赖 `uncalled-for` 是正常的依赖注入库（已核实非投毒包）。
- **MySQL 会话设置的多条语句不能逗号拼接**：`SET SESSION max_execution_time=X, SESSION TRANSACTION READ ONLY` 是非法语法（1064）——`SET TRANSACTION READ ONLY` 是独立语句、不是变量赋值。必须用 connect 事件监听器逐条 execute。此 bug 只有真实 MySQL e2e 才暴露，SQLite 单测发现不了；已抽 `mysql_session_statements()` 纯函数 + 回归测试（test_engines.py）。**教训：DB 方言相关代码，SQLite 单测不够，必须对目标 DB 跑真实 e2e。**
- **大 DELETE/UPDATE 报 2013「Lost connection ... read operation timed out」的根因与修法**：MySQL 的 `max_execution_time`（`mysql_session_statements` 设的）**只约束 SELECT，不约束 DELETE/UPDATE/DDL**——所以长写操作没有服务端语句超时，只被 pymysql 的 **socket `read_timeout`（原来 reader/writer 都 = `statement_timeout_s`=30s）** 打断成 2013。修法：**按角色分超时**（`engines.role_timeouts`）——reader 的 socket 超时用 `statement_timeout_s`，**writer 用新增的 `policy.write_timeout_s`（默认 600s，连接可配）**；PG 的 `statement_timeout` 对所有语句生效，writer 也换用 `write_timeout_s`。放大写超时让正常大写跑完，跑飞的写用**查询台取消按钮 KILL**（见下条）。真实 MySQL e2e：`scripts/e2e_serial_cancel.py`（`DO SLEEP(n)` 模拟长写——DO 非 SELECT 故 max_execution_time 不管它，忠实复现 DELETE 场景）。
- **查询台 SQL「忙时拒绝」+ 计时 + 取消（`jobs.py::JobManager`）**：后台异步查询原本每个 job 起一个 daemon 线程、无序并发。**同一 key（=连接）一次只跑一条 SQL，忙时新提交直接 `raise Busy` 被拒**（一开始做过 FIFO 排队，但排队位置对使用者不清晰，改成明确拒绝——「该连接有查询正在执行，请等待或取消后再试」）；不同连接、workflow/画布（`object()` 唯一 key）各自并行、不互拒。前端 `run()` 另加同 tab 守卫（本 tab 在跑就 flash 拒绝，避免同 tab 重入的竞态）。**取消**：调用 `engines.make_canceller`——MySQL `KILL QUERY <thread_id>`、PG `pg_cancel_backend(pid)`、SQLite `interrupt()`，在**另开连接**上发（SQLite 例外，对同一连接 interrupt）；取消器经 `run_query/run_write` 的 `on_start` 回调注册。计时用**客户端秒表锚定服务端 `elapsed_ms`**（`jobRunAt = Date.now()-elapsed_ms`，平滑且刷新后续接准确，别纯靠轮询值会显得偏快）。执行状态图标用 **Monaco 字形装饰画在被执行语句起始行**（`execLineFor` 要跳过语句区间起点的前导空白/换行，否则错位到上一行），不再固定在编辑器第一行。**出错/取消也进结果 tab**（红色「✗ 结果 N」页），与成功结果统一；**关闭结果 tab 只切换展示、绝不触发重查**（旧 bug：`closeResult`→`selectResult` 对已释放数据的邻页自动重跑）。真实 MySQL e2e + 浏览器 e2e 全过。
- 真实 MySQL 9.5 e2e 已验证通过：reader 只读防线报 1792、writer 双账号写入、information_schema 行数估算、索引命中风险判定、完整拒绝—重提审批闭环、管理后台批准。
- **防「大表拉挂 DB」用注入 LIMIT，别用流式游标**：pymysql 默认缓冲游标会把整个结果集读进客户端内存，`SELECT * FROM 大表` 无 LIMIT 时把进程/DB 拖挂。试过 `stream_results=True`（SSCursor）——但提前 fetchmany 后关连接、连接归还池复用会报 `Previous unbuffered result was left incomplete` / commands out of sync。**正解：给缺 LIMIT 的顶层 SELECT/UNION 注入 `LIMIT max_rows+1`（`engines.paginate_sql`，sqlglot AST，用户自带 LIMIT/非 SELECT 不动），让 DB 只返回这么多行，缓冲游标即安全、池复用干净**。查询台在此基础上做 LIMIT/OFFSET 分页（取 page_size+1 探测下一页，走 `_read` 不受连接 max_rows 二次截断）。
- **未绑定 database 的 MySQL 连接不能直接反射**：SQLAlchemy `inspect(engine).get_table_names(schema=None)` 在无默认库时，取 `SELECT DATABASE()` 得 None，`_escape_identifier(None)` → `None.replace(...)` 崩（报 `'NoneType' object has no attribute 'replace'`）。修法：查询台对未绑库的 MySQL/PG **先列库**（`engines.list_databases` = `inspect().get_schema_names()` 过滤系统库），选库后 `get_table_names(schema=db)` / `describe_table(table, schema=db)` 带 schema 反射；`service.list_tables(schema=None)` 对无库连接直接抛清晰错误而非让它崩。这也是 DataGrip 的库→表→列三级树。
- **子进程活着时别 read() 它的管道**：SSHTunnel 隧道就绪超时路径先 `stderr.read()` 再 close——ssh 还活着时 read() 阻塞到进程自行退出（DNS 挂起时数分钟），把探测/全量测试整个卡死；且该 bug 被网络环境掩盖（ssh 秒败走"提前退出"分支不触发），只在 DNS 变慢的日子爆发。正解：**先 terminate/kill 子进程再 read**（进程死后 read 立即 EOF 且保留已缓冲内容）。排查特征：进程 CPU 时间停住不涨、wall clock 在走 = 阻塞在外部 IO。
- **后台任务线程必须 daemon**：admin 异步查询最初用 `ThreadPoolExecutor`——它的工作线程**非 daemon**，每个 test_admin 用例 mount_admin 都建一个池，pytest 用例全过却在退出时挂死（表现为"全量测试跑不完"，极难定位）。改为 `threading.Thread(daemon=True)` 逐任务起线程。凡常驻服务里的辅助线程（housekeeping、job worker）一律 daemon。
- **Monaco 无构建 vendoring 的坑**：① Monaco 的 AMD loader 运行时按路径拉几十个文件，静态路由必须支持子路径（`{path:path}`）；② web worker 用 data-URI `importScripts(workerMain.js)` 加载，若静态路由带 `@guard`，worker 请求带不上 cookie 会被 303 到登录页而崩——所以 `/admin/static/*` **不加鉴权**（都是公共库文件、无敏感数据）；③ 用 `automaticLayout:true` 让 Monaco 自适应容器尺寸，省去手动 layout。装法：`npm registry` 取 `monaco-editor` tgz 解 `package/min/vs` 到 `static/monaco/vs`。
- **前端全屏页别用 `position:absolute;inset:0` 铺满**：会相对视口定位、盖住后台左侧导航栏。用 `height:100vh` 让它待在 `main` 网格列内即可。
- **细滚动条只用 `scrollbar-width:thin`，别用 `::-webkit-scrollbar` 自定义尺寸（真实反馈：默认横向滚动条压住查询台 tab 名字，改细时两次没改对）**：macOS 开「始终显示滚动条」时默认经典滚动条又粗又实。第一版加 `::-webkit-scrollbar{width/height:9px}`+thumb `border:2px transparent;background-clip:content-box`——**用户仍嫌粗**。根因：**一旦用 `::-webkit-scrollbar` 自定义尺寸，Chrome 就把细长的「叠加式(overlay)」滚动条强制变回带凹槽、占位的「经典」滚动条**，即使写 6px 也带槽、视觉更重；而且它**覆盖 `scrollbar-width:thin`**。正解：**只留一行标准属性 `.dg-root,.rd-root,.dg-root *,.rd-root *{scrollbar-width:thin}`**，让浏览器渲染原生细长条，全站统一（tab 条/结果网格/树/SQL 执行记录面板一致），别碰 webkit 伪元素。Monaco 用自绘滚动条不受影响。**排查特征：自动化浏览器多用 overlay 滚动条(auto-hide)，静止不显示、`offsetHeight-clientHeight≈1px`——量不出「始终显示」环境下的真实粗细，得靠用户环境确认。**
- **自家静态文件（console.js/css）必须 `Cache-Control: no-cache`**：曾设 max-age=86400，迭代时浏览器一直跑旧 JS，连坑三次（新功能"没生效"、旧 bug"复现"，其实全是缓存）。现在静态路由区分：vendor（monaco/、vue.*，内容不变）长缓存，其余 no-cache（每次带 If-None-Match 校验，改完即生效，无需硬刷新）。
- **合成打字对代码编辑器（CodeMirror/Monaco）不可靠**：浏览器自动化 `type` 会掉字符；e2e 验证时用 `javascript_tool` 直接 `monaco.editor.getModels()[0].setValue(...)` 或 CM 的 `setValue`。
- **DuckDB 的 `DROP TABLE IF EXISTS` 遇同名 VIEW 报类型错**（IF EXISTS 只豁免"不存在"，不豁免"类型不符"）：删数据集必须先查 information_schema 拿 table_type 再按类型 DROP（analysis.drop_dataset）。
- **MySQL DECIMAL 快照进分析工作区会变字符串**：`engines._jsonable` 把 Decimal 转 str，DuckDB 导入推断成 VARCHAR，`sum()/avg()` 报 Binder Error。修在 `analysis._infer_types`：某列非空值全是数字字符串 → 推断 DOUBLE（回归测试 test_decimal_strings_become_double）。真实暴露路径：DAG 聚合节点对 amount 求和。
- **UMD 库必须放在 Monaco loader.js 之前加载**：loader.js 定义了全局 `define.amd`，其后加载的 UMD 包（如 echarts）会走 AMD 注册而**不挂 window.xxx**，表现为"脚本 200 加载成功但全局变量 undefined"。修法：`<script>` 顺序上把 UMD vendor 放到 loader.js 前面（见 admin.py `_console_body`）。
- **顶层 `UNION`/`UNION ALL`/`INTERSECT`/`EXCEPT` 被误判为写操作**（真实反馈：一条正常的 UNION ALL 只读聚合查询被打进审批流）：sqlglot 把 `SELECT … UNION ALL SELECT …` 解析成顶层 `exp.Union` 节点（**不是** `exp.Select`），而 `classify` 的 `_READONLY_ROOTS` 白名单只有 `(Select, Show, Describe)` → 落到"非只读根 = 写/DDL"的兜底分支。修法：白名单加 `exp.SetOperation`（该基类覆盖 Union/Intersect/Except 三种集合运算；本版本 sqlglot 里 Intersect/Except **不是** Union 的子类，共同基类是 `SetOperation`）。安全性不打折——各分支若藏写节点/危险函数/`FOR UPDATE`，仍由后面的整树 `walk()`（`_WRITE_NODES`/`_unsafe_function_name`/`Lock`/`Into`）兜住（回归 test_classify.py::TestSetOperationGuards：UNION+SLEEP、UNION+CTE INSERT、UNION+FOR UPDATE 仍判写）。**教训：只读白名单要按 sqlglot 的顶层节点类型枚举，集合运算是独立的 SetOperation 根、别只想着 Select**；`paginate_sql` 早就认 `(Select, Union)` 了、classify 漏了。
- **sqlglot 的 TokenizeError 不是 ParseError**：引号不闭合等词法错误在**分词阶段**抛 `TokenizeError`，不是 `ParseError`；二者都继承 `sqlglot.errors.SqlglotError`。`classify`/`assess` 只 catch `ParseError` 会让非法 SQL 直接抛异常冒泡（agent 的 execute 走 server.py 只 catch QueryRejected/KeyError/ValueError → 变 500；违反「默认拒绝」红线）。**必须 catch 基类 `SqlglotError`**，任何解析/分词失败都默认拒绝按写操作/最高风险处理。回归测试见 test_classify.py::test_tokenize_error_rejected_not_raised、test_risk.py::test_tokenize_error_is_critical_not_raised。
- **sqlglot 与 MySQL 对 `DROP PARTITION` 语法要求恰好相反（真实反馈：`ALTER TABLE t DROP PARTITION p1, p2, p3` 编辑器标红 + 执行被拒，加括号后编辑器不报错、执行又被 MySQL 1064 拒）**：MySQL 正确语法是**不带括号**的逗号列表 `DROP PARTITION p1, p2`；但 sqlglot 的 mysql 方言**只认带括号** `DROP PARTITION (p1, p2)`（连单个分区都要括号，实测 30.12/30.14 均未修）。于是无括号原文喂 sqlglot 报 `ParseError: Expecting (`——`classify`/`assess`/编辑器 lint 三处都因此把合法 DDL 误判：lint 标红波浪线、classify 返回 `statement_kind=ParseError` → `admin_run_sql` 走 `kind:"error"` 分支**根本不发到 DB**（用户看到的"执行也报错要括号"其实是本地 sqlglot 的错、不是 MySQL 的错）；加括号后 sqlglot 能解析（不报错、判为 Alter 写），但真发到 MySQL 时 `DROP PARTITION (...)` 被 1064 拒。**修法：`classify.normalize_sql_for_parse(sql, engine)` 仅在喂给 sqlglot 做静态解析判定前，用正则把无括号列表临时补上括号；执行永远走用户原文**（`split_statements` 纯文本切分 + `run_write` 原样 `text(stmt)` execute，不经 sqlglot re-render，所以发给 MySQL 的还是无括号的合法语法）。三处调用点：`classify`/`risk.assess`/`admin._lint_one` 都过 `normalize_sql_for_parse`。**只处理 mysql**（`TRUNCATE PARTITION` 无此病——sqlglot 走 Command 回退、不 ParseError，且本就走原文执行）。回归：test_classify.py::TestMysqlDropPartition、test_risk.py::TestMysqlDropPartition、test_admin.py::test_lint_mysql_drop_partition_no_paren + 真实 MySQL e2e `scripts/e2e_drop_partition.py`（无括号原文真删分区 + 带括号被 1064 拒，证明必须发原文——SQLite 单测测不出方言语法）。**教训重申：给 sqlglot 解析和给 DB 执行是两条路，方言语法不一致时归一化只作用于前者、执行必须用原文。**
- **Vue 模板只能访问 data()/computed/methods 声明的属性**：命令式 `this._docCmd = x` 赋的属性**不是响应式、模板里也取不到**（`{{ _docCmd }}` 直接 ReferenceError 让整个组件 render 崩、白屏）。要在模板显示的中间状态必须在 `data()` 里声明。排查白屏第一步永远是看浏览器 console 报错（这次连踩两个：`countLeaves 未定义`的模块级辅助函数漏写、`_docCmd`未声明——都表现为整页白屏只剩侧栏）。
- **共享控件要真的共享：Redis 控制台曾把连接/库下拉留成原生 `<select>`**（真实反馈：「和 db 不统一」）。`dg-select.js` 的注释早就写着「查询台 / Redis / 流程页共用」、页面也确实加载了这个脚本，但 `redis.js` **从没 `app.component("dg-select", …)` 注册过**，两个下拉一直是原生 select——深色 IDE 里唯一一块系统外观的控件。修法：redis.js 注册组件 + 加 `connOptions`/`dbOptions` 计算属性（连接带环境徽章、库带键数）+ 换掉两处 `<select>`；redis.css 里 `.rd-conn select` 那套手写样式删掉，只留宽度。顺手把查询台 AI 面板里最后一处原生 select（库选择器）也换了。**排查手法：`grep -an "<select" static/*.js` 一次找齐全部残留**——共享组件的「已共用」只能靠这种全局搜索证明，不能信注释。随后 workflows 的 8 处（节点配置的 WHERE 列/运算符、图表类型/X/Y/聚合，调度对话框的频率/通知策略）也一并换掉，**全站已无原生 `<select>`**。两处配套能力：① `dg-select` 加 `drop="up"`（`.dg-sel.up .dg-sel-pop{top:auto;bottom:105%}`）——贴在容器底部的选择器（Redis 库切换器）必须用，否则弹层向下冲出面板被 `overflow:hidden` 裁掉半截；② 加**分组标题**支持（选项带 `group` 字段 → `rows` 计算属性插入不可点的 `.dg-sel-group`），替代原生 `<optgroup>`，否则图表类型那 13 个选项换过来会丢掉「基础/多列/统计/业务」的分组。

- **Redis 控制台单开一页而非融进查询台**：查询台是深度面向 SQL 关系模型的（分页/WHERE/列头排序/单元格编辑/图表/DAG/schema 选择器…），Redis 是键值模型，硬塞会到处 `isRedis` 条件分支、回归风险高、两边互相牵制。独立页 `/admin/redis`（`redis.js`/`redis.css`）资产级复用 console.css 外壳 + `--dg-*` 变量 + `.dg-btn`，两个工具各自简单。**教训：两种数据模型差异大时，单开一页的少量基础设施重复，远比塞进一个控制台的隐性复杂度便宜。**
- **ProxyJump 的两个坑（多跳 e2e 踩出）**：① 命令行 `-o` 选项只作用于最终目标、不传递给跳板连接——自定义密钥/known_hosts 必须用 `-F 配置文件`（对链上每跳生效），对应 `ssh_options: ["-F", path]`；② sshd_config 是**首个匹配生效**，往文件末尾 append `AllowTcpForwarding yes` 无效，容器里用 `sshd -o` 命令行覆盖。多跳验证脚本：`scripts/e2e_ssh_multihop.sh`（两级 sshd 容器链到本地 MySQL，凭证全程隔离在 /tmp）。
- **每跳独立证书 = 生成 `ssh -F` 配置，不能靠命令行 `-i`**：`jump_hosts` 是结构化 `list[JumpHost]`（host/user/port/`identity`引用证书库或内联`key_path`/`known_hosts_path`），旧的裸字符串 `"user@host:port"` 由 `JumpHost` 的 before-validator（`parse_hostspec`）兼容解析——所以老 YAML/e2e 全不用改。隧道层（`tunnel.py`）分两条路：**无任一跳带 key** 走遗留 `-J`（不生成临时文件、行为不变，保护现有 e2e）；**任一跳带 key** 走 `build_ssh_config` 生成临时 ssh 配置（`Host *` 放 BatchMode 等全局项对每跳生效，每跳 `Host dbmhopN` 带自己的 IdentityFile/UserKnownHostsFile + `ProxyJump` 串链），`ssh -F <tmp>`，`close()` 时 `os.unlink`。证书库存 YAML 顶层 `ssh_identities`（只存路径引用、不存密钥内容），引擎池/Redis 池各持 `AppConfig.ssh_identities` 的**活引用**（`self.pool.identities = self.config.ssh_identities`，同一 dict 原地增删即时可见，避免 14 处 `pool.get` 逐个透传）。删证书时被连接引用则拒删（`identity_referers`）。**每跳不同证书只能真实 e2e 证明**：`scripts/e2e_ssh_multihop_percert.sh`（jump1 只认密钥A、jump2 只认密钥B，正向查通 + 负向把 jump2 换密钥A 必须失败——单测测不出证书是否真被分别使用）。后台连接表单跳板改**可增删的行**（每行选证书或内联 key，纯 JS clone `<template>`），证书库在系统设置「SSH 证书」tab（`?tab=ssh`）。

- **左树「不够清晰」的三个具体成因，与配色无关的那两个更要紧**（真实反馈）：① **区标题不是标题**——`.dg-sec-hd` 是 10.5px 的 `--dg-faint` 等宽字，还套了 `text-transform:uppercase`（**对中文完全无效**，等于白写），于是占了 90% 面积的「表」区标签反而最弱，区与区之间也没有任何分界线；② **元信息压住了主角**——行数估算 `<0.1 M`、列类型 `VARCHAR(32)` 与标识符几乎同粗同色，而树里「名字才是对象」；③ 图标五种颜色五种风格（同侧栏导航的毛病）。修法：区标题改**非等宽 + 600 字重 + `--dg-text`**、区间加发丝分界线（`acc-hd{border-top}`，`:first-child` 去掉）；元信息退到 10px `--dg-faint` + `tabular-nums`；图标统一线框并走 CSS mask，**只给「表」一个强调色（琥珀＝这是一张表）、其余中性灰**——扫视时眼睛要找的就是表；选中态从通栏实色蓝改成圆角胶囊 + 淡底 + 1px 描边；分组行（`tables/columns/keys/indexes`，模板里恰好都带 `.sub` 类，不需要 `:has()`）降级成树内小标题。**教训：`text-transform:uppercase` 在中文界面里是纯装饰、给不了任何层级——中文的层级只能靠字重/字号/颜色/分界线做出来。**

- **三态配置（连接级覆盖全局）不要让 `None` 被当成 `False`**（脱敏开关踩到）：把 `Policy.mask_default_patterns` 从 `bool=True` 改成 `bool|None=None`（None＝跟随全局设置）后，`masking.py` 里原来的 `if policy.mask_default_patterns and …` 会把「跟随全局」**静默当成关闭**——安全开关被悄悄关掉，还没有任何报错。修法：把「是否启用」变成 `apply_mask(..., default_patterns: bool)` **显式入参**，并提供 `resolve_default_patterns(policy, global_default)` 供调用方先定值；masking 模块自己不再读那个三态字段。**教训：三态字段一旦引入，所有 `if x.flag` 的真值判断都是 bug；要么全改成显式解析后的 bool 入参，要么用 `is None` 逐个判。**

- **给 LLM 是脱敏、给人是真实值，这条线现在可配了**：`mask_sensitive_columns`（系统设置 DB tab，默认开）+ 连接级三态覆盖，**只影响 agent 的 `query`/`sample_rows`**；后台查询台与导出走 `_read(mask=False)`，任何开关下都是真实值（回归 test_mask_config.py::TestConsoleAlwaysReal）。关掉的只是「按 password/token 这类词猜」，连接上手动点名的 `mask_columns` 始终脱敏。

- **⌘F 网格命中高亮改了三版才对，两个独立问题**（真实反馈先「根本看不清」、再「深黄色高亮太丑」）：
  - **技术问题（看不清的一半原因）**：命中格同时可能带 `.rcur`（当前行）/`.csel`（单元格选区）/`.vsel`（值编辑，自带 `!important`）/`.edited` 的底色，按 CSS 特异性它们**会盖掉命中高亮**——实测计算值拿到的是 rcur 的蓝色 14%，而不是命中态设的颜色。修法：选择器提到 `table.dg-rt tbody td.curhit` 并对 background/color 加 `!important`；「我搜的那一个在哪」必须永远压过其它单元格状态，这里的 `!important` 是有意为之、注释里写了原因。
  - **审美问题**：第二版照搬浏览器「页内查找」的亮黄底 + 黑字，读是能读了，但在深色 IDE 里像糊了块荧光笔。**深色 UI 上不要把单元格整块翻成亮色**——正解是把文字提亮、底色只做很淡的暖色抬升，对比靠**描边**给：其余命中只有一层 12% 的暖色底（71 个命中同时描边反而看不出当前在哪），**只有当前命中有那一圈琥珀环 + 一点外扩微光**，层级差完全由「谁有环」拉开。
- **树的展开箭头别用 ▸▾ 字形**（真实反馈两轮「看不见」→「还是不够明显」）：这两个字符（U+25B8/U+25BE）的实际墨迹远小于字号，12px 也依旧糊，且各字体渲染差异大——把字号往上堆解决不了。正解是**用 CSS 画 chevron**：一个方块只留 `border-right/bottom`、`transform: rotate(-45deg)`，粗细（`--tw-stroke`）与大小（`--tw-size`）完全可控，展开时转成 `rotate(45deg)` 顺带得到一个自然的微交互。**代价是状态要进类名**：CSS 选不到「文本内容是 ▾ 还是 ▸」，所以模板里 12 处 `<span class="tw">{{ x ? "▾" : "▸" }}</span>` 都要补 `:class="{open: x}"`（原文字用 `font-size:0` 藏起来作兜底）。

- **多图标导航要「单色 + 单一强调色」，图标用 CSS mask 而不是 background-image**（真实反馈：第一版加宽带标签后仍被判「样式不够好看」）：问题不在尺寸而在**颜色与风格的熵**——七个导航图标各自带色（青/红/紫/蓝/绿/琥珀/灰）、线框与实心混用，加上选中态是一整块实色青，同屏看下来既没有层级也不成体系。修法：① 图标改用 `-webkit-mask-image`/`mask-image` + `background-color: currentColor`，**形状由 mask 给、颜色由 color 给**，于是 idle/hover/active 只需要改一处 `color`，图标自动跟随（用 `background-image` 时每个状态都得换一套带色 SVG，根本做不了状态联动）；**mask 用的 SVG 描边必须是白色**——`mask-mode` 在 alpha 与 luminance 两种解释下白色都可见，黑色在 luminance 模式下会整个消失。② 七枚图标统一重画为 16×16 / 1.5 线宽 / 纯线框；**小尺寸下闭合小图形会被线宽填满**（Redis 的分层菱形、DAG 的节点圆一开始都糊成实心块），要把图形放大、留出至少 ~2.5 个单位的内部空白。③ 选中态从实色块改成半透明底 + 左边缘一根带微光的窄条——把「重」只留给唯一一个该被看见的元素。**教训：导航「不好看」通常不是尺寸问题，是同屏色相数量太多；先把颜色收敛到一个强调色，再谈别的。**

- **连接「不会自愈」的根因是把 exhausted 当终态**（真实反馈：DB 恢复了页面还是连不上，只能人工点重连）：`health.py` 原来退避 5 档用尽就 `state=exhausted` 并**永久放弃**——后台重连线程 `return` 退出，而 `check()` 又会挡下所有触达 DB 的调用，于是「没人再试一次」，DB 恢复也无人发现。改成**断路器三态 + 永不放弃**：① 退避阶梯用完后**保持最长一档持续重试**（封顶取 60s——不再有终态放弃后，封顶即「DB 恢复后最坏多久自动可用」），exhausted 退化为「需要人看一眼」的标记而非死路；② `check()` 在 `now >= next_retry_at` 时**放行一个真实请求去探路**（half-open），成功即 `mark_ok` 自愈、失败即 `mark_failed` 重排退避；③ 探路名额用 `probing` 标志与后台线程互斥、避免并发重复打 DB，并配 `PROBE_LEASE_S`(120s) 租约防「探路者没回报成败把连接永久锁死」；④ 后台线程改**分段睡**（`_TICK_S`=1s）才能对 `stop()`/`next_retry_at` 变化及时响应（原来死睡到点）。真实 MySQL 容器 e2e：`docker stop` → 报错打标 → `docker start` → **5 秒内无人工干预自动转 ok**。**教训：带退避的重连不要设「终态」，只设「退避上限」——外部依赖恢复的时间不可预测，放弃等于把自愈责任推给人。**
- **连接不可用时的重连入口必须在错误发生的地方**（真实反馈：「页面上难以操作重连」）：`reconnect` 功能一直都在，但只挂在**左树库节点的右键菜单**里，出错时结果区、连接选择器上一个字都没有，等于没有。修法三处：① 新增 `GET /admin/sql/health`（只返回**非 ok** 的连接，健康的不占带宽）→ 查询台每 10s 轮询，`dg-main` 顶部挂**告警条**（连接名 + 「后台正在自动重连，约 N 秒后再试」+ 最近错误 + 「立即重连」按钮）；② 后端把错误分类透传给前端——`admin.error_payload()` 给连接类错误打 `error_kind`（`connection_unavailable`/`connection_exhausted`/`connection_error`，最后一种覆盖「健康位还没来得及打标的第一次失败」），异步任务路径靠在异常上挂 `dbm_error_kind` 属性穿过 `JobManager`（管理器本身不认识具体分类，保持通用）→ 结果区错误页直接长出「↻ 重连数据库」按钮；③ 编辑区 tab 组头加连接状态点。**告警条要留出右侧 64px 给固定定位的全站铃铛**（`.dbm-bell` z-index 9999），否则按钮被压住。**教训：功能存在 ≠ 可用；「出错时人下一步要点什么」必须出现在错误旁边，不能藏在右键菜单里。**
- **agent 侧 SQL 语法预检：sqlglot 只能做初筛，判死必须由 DB 复核**（`engines.dry_run_syntax_check` + `service._syntax_precheck`）。只信 sqlglot 会误拒合法方言语法（本仓库已踩过 `ALTER TABLE t DROP PARTITION p1, p2`）。做法：classify 得 `statement_kind=="ParseError"` 时，让目标库**只解析不执行**地复核一次——MySQL `SET @v=:sql; PREPARE … FROM @v`（覆盖 DML+DDL，最完整）、SQLite `EXPLAIN`（只编译不执行）、PG `PREPARE … AS`（**只支持 DML，DDL 会被误报语法错 → 直接标为「无法复核」不碰**）、ClickHouse `EXPLAIN SYNTAX`（只 SELECT）。**关键判定规则：只有 DB 报「语法错」这一类才拒，其它错误一律视作「语法没问题」放行**——真机验证了这条规则的价值：`HANDLER orders OPEN` 是合法 MySQL 但 PREPARE 协议不支持，MySQL 报 **1295**（不是 1064），按规则被正确放行；`CHECK TABLE orders` 同样合法且 sqlglot 解析不了，也未被误拒；只有真打错的 `SELCT * FROM orders` 被精确拒绝。效果：`query` 的语法错不再回一句误导性的「仅允许只读语句」，`execute` 的语法错**不再生成审批单**（不浪费人工审批），而 sqlglot 认不出但 DB 认的语句仍走原有「默认拒绝 → 审批流」兜底、能力不减。**教训：静态解析器和目标 DB 是两套语法，凡要「据静态解析结果判死」的地方，都得给 DB 一次翻案机会。**
- **查询台的「结果页」操作必须锚定到结果本身，不能用编辑器全文**（真实反馈：结果页点导出被「导出仅支持只读查询」拒掉）：导出按钮所在的工具条是按「当前展示的结果」渲染的，但 `exportAs` 发的却是 `currentSql()`（编辑器全文）——编辑器里只要有一段注释+一条 SELECT（多语句），classify 就判成 MultiStatement 进审批流，导出被拒。修法：新增 `resultSql(t)`——查询 tab 取 `results[resultIdx].sql`（产生这一页结果的 SQL，必是单条只读语句），数据 tab 取 `readSql`（含 WHERE/排序/分页），都没有才回退到全文。**同一条规则适用于一切「对当前结果施做」的操作**：分页、复制选中行、图表都只该认这一页结果，编辑器全文只服务于「写新 SQL」。顺手补上 PG 的 `db` 一并随导出请求走（结果在哪个库就得去哪个库导）。
- **结果表列宽「自适应」= 按内容来，不是拉满整宽**（真实反馈：`table.dg-rt` 原来是 `width: max-content; min-width: 100%`——列少时表格被 `min-width:100%` 拉满容器、多余宽度按浏览器自动布局**任意分配**给各列，`active` 列能比 `name` 列还宽，看起来像没自适应）：去掉 `min-width: 100%`，表格按内容宽度左对齐，多余区域留白（和 DataGrip 一致）；单格 460px 上限 + 省略号 + 值面板看全文的策略不变。
- **单元格就地编辑的输入框要与格子完全贴合**（真实反馈：输入框和格子之间有缝）：`td` 有 `padding: 4px 10px`，输入框再带自己的 border/radius，两层之间就是可见缝隙。修法：给被编辑的 `td` 加 `editing` 类 → `padding: 0`，输入框 `box-sizing: border-box; width: 100%; height: 25px`（行高恒 27px = 12px 字 / 18px 行高 / 4+4 内边距 / 1+1 边，输入框占内容区 25px，行高不变不跳格），并去掉 `min-width: 80px`（窄列里它会撑出格子）。
- **PG 跨库的「取表结构」链路必须一路带上 database**（真实反馈：AI 生成 SQL 时选了表，报「表 'device_installed_app' 不存在，可用表: （无）」）：前端 AI 面板拉表列表用的是 `dbQs()`（带 `&db=`），但**生成**时 `aiGenerate` 只发了 `schema`、没发 `db`；后端 `ai_generate_sql` 也只 `pool.get(project, connection, cfg)`——于是引擎落在**连接默认库**，用户在别的库选的表反射不到，`_ensure_table_exists` 拿到空表清单。修法三处对齐：前端按 `connMeta.engine==='postgres'` 发 `db`（非 PG 不发，`resolve_pg_database` 会拒）；`/admin/sql/ai` 透传 `database`；`ai_generate_sql` 先 `resolve_pg_database` 校验（不存在的库明确报「不在可连接的库中」，不当断连打坏健康位）再 `pool.get(..., database=)`。**同类链路都要查**：`sample_rows` 以前也不收 schema——PG 表在非默认 schema、MySQL 在非默认库时样本被 `except: continue` 静默丢弃（AI 少了样本行），已补 `schema` 形参并在 AI 取样本时传入。真实 PG 双库 e2e（docker）：默认库只有 `leftover`、`otherdb.app.device_installed_app` 在另一个库，不带 database 精确复现「可用表: （无）」，带上后 DDL+样本都取到。**教训：凡是「树/面板里看得到的东西」，后端操作必须走同一条库/schema 上下文；前端看得见、后端取不到，一定是中间哪一跳漏了上下文参数。**

- **agent 侧错误必须有唯一出口**（`errors.py` + `server.py::agent_error`）：原来各工具 `except` 子句五花八门，`query`/`execute` 只 catch `(QueryRejected, KeyError, ValueError)`，pymysql 的 1064/1146/1142 直接冒泡——既泄漏 SQLAlchemy 拼进消息的 **DSN（含明文密码）、绑定参数、`(Background on this error at: …)`**（破「密码不落工具返回值」红线），又让 agent 收到没法行动的噪音。修法：`errors.py` 纯函数按**驱动错误码优先、消息片段兜底**归成 `sql_syntax_error`/`table_not_found`/`permission_denied`/`query_timeout`/`deadlock`… 十余类，每类配一句「该怎么办」，`sanitize_db_message` 剥掉 `[SQL: …]`/`[parameters: …]`（**从第一个标记到结尾整段截掉**，二者恒在末尾）、背景链接、DSN 里的账号密码；`server.py` 的 17 处 except 全部收敛成一句 `except Exception as e: raise agent_error(e) from e`，`execute` 的**等待期批准后执行**也一并纳入同一个 try（原来在 try 外，批准后落库才暴露的锁超时/约束冲突会裸奔）。**教训：错误处理的分散程度 = 泄漏面积；给外部（agent/前端）的错误应当只有一个出口函数。**
- **按「行号」存的前端状态，必须在结果集换掉的每一处一起作废（真实反馈：数据 tab 加 WHERE + 排序后整页白屏）**：查询台里 `rowSel`/`cellSel`/`curRow`/`vsel`（Value Editor 选中格）/`edits`/`dels` 全都以 `ri`（当前这一屏的行号）为 key，而行号只在**产生它的那一份结果**里有意义。`run()` 里原本清了前三个、**独独漏了 `vsel`** → 重查后行数变少时 `t.result.rows[t.vsel.ri]` 是 `undefined`，`vpDirty()` 又是在**模板里**被调用（`:disabled="!vpDirty()"`），于是 `undefined[ci]` 抛在 render 阶段 → Vue 整棵组件树渲染失败 → **页面只剩侧栏的白屏**（控制台 `TypeError: Cannot read properties of undefined (reading '1') at Proxy.vpDirty`）。修法三层：① 抽 `clearSelState(t)` 一次清干净，在**所有换结果集的地方**都调用——`run()`、`selectResult()`、`closeResult()`（后两个原本一处都没清，切结果页同样会崩）；② `vpRow()` 兜底：选择失效返回 null，`vpDirty/vpSave/vpRecord` 与面板的 `v-if` 全走它，任何遗漏路径最多是面板消失、不会白屏；③ **`edits`/`dels` 是同一个 bug 的数据损坏版**——它们跨重查存活，而 `pkConds(t, ri)` 是拿**当前**结果第 ri 行的主键去生成 UPDATE/DELETE 的：先在 A 结果上暂存改动、再换 WHERE/ORDER BY/翻页，提交就会**改错行、删错行**。加 `rowsetSig(t)`（conn+schema+db+table+where+orderBy+page）在暂存第一处行改动时打戳，`buildPendingStatements` 比对不一致即拒绝（不静默丢弃用户的改动，让人自己点 ↻ 放弃并刷新）。**教训：白屏第一步永远是看控制台栈顶那个方法名——它直接指出是哪份「按索引取值」的状态过期了；而同一份过期状态，在渲染路径上是白屏，在写路径上是改错行。**

- **grep 在这个仓库的部分 UTF-8 文件上会静默失败（排查工具坑，非产品 bug）**：`grep -n "reconnect" static/console.js` 返回空且退出码 1，一度让我误判「重连 UI 被某次重构删掉了」，实际它一直在（`console.js:1800`）。根因是该文件被当成二进制处理。**排查这些前端大文件一律加 `-a`（或 `LC_ALL=C grep -a`）**，否则会得到假阴性并据此做出错误结论。

- **会话内确认（elicitation）弹窗的两个可用性硬伤，都不是「文案问题」而是协议/长度问题（真实反馈：一个「不好操作」、一个「根本看不到也无法操作」）**：① **别用 `ctx.elicit(msg, response_type=["approve","deny"])`**——FastMCP 对这种标量/枚举写法生成的 schema 带 `required: ["value"]`，Claude Code 就渲染成一个必须先填的字段，弹窗上出现红色「⚠ Value: not set / This field is required」，人得先上下键把值选出来才允许 Accept，看着还像出错。正解：**传一个所有字段都有默认值的 BaseModel**（`ApprovalDecision.decision: Literal["approve","deny"] = "approve"`），pydantic 就不会把它放进 `required`，Accept 直接可点、含义即批准；字段仍留着，人想显式选 deny 也行。**注意 `response_type=None` 不是出路**——fastmcp 已把空 schema 标为 deprecated（某些客户端会卡在空表单上）。② **message 必须裁到一屏**：客户端把整段正文原样打在终端里，`sync_table` 的整份计划（带 `CREATE TABLE` 十几行）会把 Accept/Decline 按钮顶出可视区，人连点都点不到。`_clip_block` 同时卡**行数(8)/单行长度(100)/总字符(480)**三条——终端会折行，只卡行数挡不住撑爆屏幕——并附上审批页链接让人去看全文。回归见 test_elicitation.py::test_elicitation_form_has_no_required_field / test_elicitation_message_stays_one_screen（断言的是真实 MCP 协议里客户端收到的 `requestedSchema` 与 message，不是拼字符串）。
- **跨引擎建表：sqlglot 直译的 DDL 目标库多半不认，必须剥干净再发（表同步功能踩出，已进 `sync.py::_strip_dialect_specifics`）**：把 MySQL 的 `SHOW CREATE TABLE` 原文 `transpile(write="postgres")` 出来看着挺像，实际四处会被目标库拒：① **表属性原样保留**——`ENGINE=InnoDB AUTO_INCREMENT=2001 DEFAULT CHARACTER SET=utf8mb4 COMMENT='…'` 会跟着输出到 PG/SQLite；② **无符号类型**——`bigint unsigned` 被解析成 `DType.UBIGINT`，写出去就是 PG 不认识的 `UBIGINT`（要降级成 `BIGINT`；按 `Type` 枚举名去掉前导 `U` 再查表最省事）；③ **`UNIQUE KEY 名字 (列)` 直译成 `UNIQUE "名字" (列)`**——PG/SQLite 都只认 `CONSTRAINT 名字 UNIQUE (...)`，这条是真机 e2e 才炸出来的（本地 `sqlite3.connect(":memory:").execute(ddl)` 一跑就报 `near ""uk_uc"": syntax error`），去掉名字保留语义即可；④ **内联 `KEY idx (列)` 二级索引**——PG/SQLite 的 CREATE TABLE 里没有这个语法，且改了表名后索引名还可能撞车，直接丢掉 + warning 最干净。另外列上的 `COLLATE utf8mb4_*` / `ON UPDATE CURRENT_TIMESTAMP` / 列 `COMMENT` 也都要剥。**教训：方言转写的正确性只能由目标库执行来证明——「转写出来的字符串长得对」是最容易骗过自己的一种验证。**
- **跨库复制数据不能走 `run_query`**：`run_query` 是给人/agent「看」的，会把 Decimal 转字符串、bytes 包成 `{"__bytes_base64__": …}`、超长单元格截断（`truncate_cell`）、还可能按脱敏规则把值换成 `***`。这些对展示无害，但作为**写进目标库的值**每一条都是数据损坏。所以复制路径单开 `engines.fetch_rows_for_copy`：拿驱动原生 Python 值、不截断、不脱敏，直接绑参写回目标表（datetime/Decimal/bytes 由目标驱动自己适配，真机验证过 MySQL→PG 的 DECIMAL(12,4)/datetime/JSON/中文/超 2^53 大整数逐列相等）。**教训：同一份数据「给人看」和「写进另一个库」是两条路，别复用展示层的取数函数。**
- **PG 的「库」和 MySQL 的「库」不是一回事，照抄 MySQL 的树会漏掉半个数据库（真实反馈：「查不到多个数据库，只有 schema」）**：`list_databases` 对 PG 走的是 `inspect().get_schema_names()`，返回的是 **schema**——于是左树对 PG 实际是「schema → 表」，同一台服务器上的别的 database 一个都看不见。根因不是查询写错，而是 **PG 一条连接只能绑一个 database，跨库查询在协议层就不存在**（`SELECT … FROM otherdb.public.t` 直接报 `cross-database references are not implemented`，跑错误矩阵时撞到过）。所以「换库」只能是「换连接」：新增 `engines.list_server_databases`（PG 查 `pg_database`，过滤模板库与 `datallowconn=false`）列库，`EnginePool` 的 key 加 **database 维度**（`(project, connection, role, schema, database)`），按选中的库另建引擎——和当初为 schema 上下文做的是同一套机制。`database` 参数从 admin 路由（`db=`）一路透到 `_read`/`admin_run_sql`/`list_tables`/`describe_table`/`get_table_ddl`/`admin_table_sizes`/`admin_search_tables`/`admin_import_rows`/`admin_explain`/权限目录查询——**漏传一处就是「树里选了 shop、SQL 却在 testdb 上跑」**（`admin_table_sizes` 一开始就漏了，真机上表现为 billing 的表列表里混进 testdb 的容量；`admin_import_rows` 漏传会把数据**写进另一个库**，性质同前面 reader/writer 分家那条）。前端左树同一时刻**只展开一个库**——同时摊开两个会暗示能跨库 JOIN，而 PG 做不到（**执行库后来改成每个 tab 各自独立**，左树跟随当前 tab，见「PG 跨库」状态条）；这样内部 key 也不用改成 `库.schema` 复合键，`qtable()` 生成的标识符不会被带歪。**教训：多引擎产品里，「库」这种看似通用的概念要按引擎各自的数据模型建模，别用一个 `schema` 参数硬套两种语义。**
- **树里「有层级关系」的两组节点，必须拍平成一个有序列表来渲染，不能分两段各自 v-for（真实反馈「树结构错位」+「点击时会跳动」）**：PG 的库这一层第一版是「先渲染 serverDbs 的全部库行，再渲染 filteredDatabases 的全部 schema 行」——两段都对，合起来就错：schema 永远落在**最后一个库**下面，而不是选中的那个（用户截图里 console/mod_config/public 挂到了 postgres 底下，实际选中的是 mod_trace）；切库时那一整块 schema 还会在列表底部上下横跳。修法是加一个 `treeRows` computed 把两种行**按顺序交织**成一个数组（`{kind:'db'|'schema'|'loading', name}`），模板对着它单层 v-for、按 kind 分支渲染。为了不把 schema 子树那二十行 markup 复制一份（MySQL 还要用同一份），schema 分支里用**单元素 v-for**（`v-for="db in [row.name]"`）把 `row.name` 别名回 `db`，下面十几处 `db` / `mk(t,db)` 一个字都不用改。**另一个跳动源是工具条的条件渲染**：`.dg-schema-tools` 原来是 `v-if="databases.length"`，而切库时 `databases` 会先清空再重填 → 工具条消失又出现 → 整棵树上下弹一次；改成 `v-if="serverDbs.length || databases.length"` 常驻即可。**残留的一格位移（点选中项下方的库时，它会上移一行）是手风琴的固有行为**（上面那个库收起了），DataGrip/pgAdmin 同理，不再处理。
- **两个只在「首次加载」才犯的前端坑（都由 PG 库这一层暴露）**：① **树缓存会把「还没加载完」的空状态固化下来**——`loadTree` 会先于连接列表跑一遍（那时 `connMeta` 还是 null，认不出引擎、什么都不拉），如果把这次的空结果写进 `treeCache` 并在下一次直接命中返回，树就永远停在空的。修法：命中缓存前先判「这份快照对当前引擎是不是空的」（PG 看 `serverDbs`），是就当没缓存、重新加载。② **把「选中」写成 toggle，初始化时会自己把自己收起**——`selectPgDb(db)` 原来做成「再点一次收起」，而初始化恰好会用当前库名调它一次 → 刚选中就被收起，表现为「库这一层一个都不显示、但 schema 却加载出来了」。这一层本来就只能开一个，收起没有意义，直接去掉 toggle。**排查特征：手动点「刷新」正常、进页面就不正常 → 优先怀疑「初始化顺序」与「缓存了未就绪状态」，别一头扎进渲染逻辑。**
- **psycopg3 的异常形态与 pymysql 不同，照抄 MySQL 的判定必然在 PG 上失效（真机 PG17 一次跑出四个）**：① **类名多数不以 Error 结尾**（`UndefinedTable`/`InsufficientPrivilege`/`AdminShutdown`），`errors.py` 剥驱动前缀的正则只认 `\w*(?:Error|Exception)`，于是 PG 的错误一律带着 `(psycopg.errors.XXX)` 外发给 agent 和查询台（用户反馈的原文就是 `⚠ ProgrammingError: (psycopg.errors.InsufficientPrivilege) permission denied for table crawl_job`）→ 增补一支「带模块路径的点分类名」。② **「列不存在」被误判成「表不存在」**——PG 两者消息都含 `does not exist`，片段匹配必然按 `_RULES` 顺序命中表规则；正解是 **SQLSTATE 优先**（psycopg 异常带 `.sqlstate`），`42703` 列 / `42P01` 表 / `42501` 权限 / `25006` 只读一目了然（57014 有意不入表：语句超时与人工取消同码，靠文案区分 `query_timeout` / `query_canceled`）。③ **PG 断连不触发自愈**：`pg_terminate_backend` / 服务重启 / RDS 维护抛的是 `OperationalError: (psycopg.errors.AdminShutdown) terminating connection due to administrator command`（57P01），落在 `health.py` 的「名字重叠类须叠加消息片段」那一支，而片段表里**一条 PG 的都没有** → `is_connection_error` 返回 False → 健康位不打标、后台不重连、DB 恢复也无人发现，agent 收到的是无法行动的 `db_error`。补 SQLSTATE（`08xxx` 全族 + `57P01/02/03`）与 PG 消息片段。④ PG 的错误消息带独立一行的插入符（`      ^`），换行折叠后纯噪音，`sanitize_db_message` 里剥掉。**教训：错误分类/连接判定这类「照着某个驱动写出来的」逻辑，每接一种新引擎都要对着真机重跑一遍错误矩阵——SQLite 单测一个都测不出来。**
- **白名单式的语法预检，恰好会漏掉最常见的那个错误**：PG 的 `PREPARE` 只吃 DML，所以 `_syntax_check_supported` 原本只放行 `select/insert/update/...` 白名单里的首关键字。但**首关键字打错（`SELCT` / `UPDTE`）正是最常见的语法错**，而它按定义落在白名单外 → 被整条跳过 → PG 上预检形同虚设（真机 `SELCT * FROM crawl_job` 实测 `supported=False`）。修法：维护一张**全部合法 PG 语句关键字**表，首词不在其中就说明不存在以它开头的合法语句，照样送 `PREPARE` 让 DB 报真实语法错（仍由 DB 判死，不自己下结论）；合法但 PREPARE 不支持的 DDL/工具类语句照旧跳过。报错回显里记得抹掉我们自己加的 `PREPARE dbm_syntax_chk AS ` 包装，否则用户会看到自己没写过的语句。**教训：写「哪些情况才检查」的门禁时，先问一句「我要抓的那个错误，会不会正好被这个门禁挡在外面」。**
- **DCL 语句自带明文密码 → 执行与审计必须是两份语句**：`CREATE USER … IDENTIFIED BY 'x'` / `ALTER ROLE … PASSWORD 'x'` 一旦按常规路径落审计就直接破「密码永不出现在审计记录中」红线。`privileges.py` 的每个构造函数返回 `DclStatement(sql, audit_sql, summary)`：`sql` 发给 DB，`audit_sql` 把密码换成 `***`，服务层审计与页面回显一律用后者。**凡是「语句文本里可能含密钥」的功能（DCL、CONFIG SET requirepass、连接串），都要在生成语句的地方就分出脱敏版，别指望下游的通用脱敏认得出来。**
- **`dg-select` 的当前项在浅色主题下是空白行**（做权限页时撞见，全站共用组件的老 bug）：`.dg-sel-item.cur` 的 `color` 写死成近白色 `#d7e3ff`，那是配深色 `--dg-accent-soft` 才成立的；浅色主题下 accent-soft 变成浅蓝，白字直接消失——下拉里**当前选中的那一项看起来是一行空白**。console.css 里早有两条同类修正（`.dg-item.sel .nm`、`vswitch button.on`），唯独漏了这个共用组件。修法一行：`.theme-light .dg-sel-item.cur{color:var(--dg-text)}`，**不挂在某个页面的根类上**——查询台/Redis/流程/用户权限四个页面都用它。**教训：把「配深色底」的颜色写死在共用组件里，等于给每个新主题埋一个雷；共用组件的颜色必须走变量。**
- **审批单的执行计划：必须带列名，且 MySQL 必须显式要 `FORMAT=TRADITIONAL`**（真实反馈：审批页只有一排裸值，看不出哪列是啥）。① `engines.explain` 从「`" | "` 拼接的纯文本」改为返回 `{"columns": [...], "rows": [[...]]}`，审批页 `admin._explain_html` 据此渲染带 `<thead>` 的表格（`.plan-tbl`，横向可滚动）；老审批单里存的是字符串，渲染器按 `isinstance(plan, str)` 走原 `<pre>` 分支，不会把首行数据误当表头。② **MySQL 9 起 `explain_format` 默认 TREE，而 TREE 解释不了 DML**——`EXPLAIN UPDATE …` 只回单列一句 `-> <not executable by iterator executor>`（本地 9.5 实测），旧代码把它当"点查无需计划"翻译成人话，其实是格式问题；改发 `EXPLAIN FORMAT=TRADITIONAL` 后拿到完整 12 列（type/possible_keys/key/rows/Extra），审批人才判得了全表扫描。其它引擎仍用裸 `EXPLAIN`。行数/单格上限 `engines.PLAN_MAX_ROWS`(50)/`PLAN_MAX_CELL_CHARS`(500) 取代原来的 `plan[:4000]` 截断。**教训：EXPLAIN 的默认输出格式是方言 + 版本相关的，SQLite 单测只能验"带不带列名"，格式对不对必须真机跑一次。**
- **写语句的 EXPLAIN 必须用 writer 账号**：`admin_explain` 原来固定用默认 reader（只读账号）取执行计划，对 `DELETE/UPDATE/INSERT` 会被 DB 以权限不足拒绝（MySQL `1142 command denied to 'agent_read'`）——EXPLAIN 虽不真正执行 DML，但服务端仍按语句所需权限校验。修法：`role = "writer" if (not verdict.readonly and cfg.writer is not None) else "reader"`（无独立 writer 才退回 reader，如 sqlite）。参照已有的 `_try_explain`（审批风险报告里的计划）本就是 reader→writer 回退。**sqlite 单测测不出**（writer 复用同库、无权限概念），靠真实 prod EXPLAIN + HTTP 级 spy 测试（`test_explain_write_uses_writer_role` 断言 DELETE 选 writer、SELECT 选 reader）证明。
- **语句分隔要认「换行」而非只认分号；lint 只标当前语句**（用户两次反馈红波浪线标错位置）：查询台里用户习惯一行一条 SQL、不写分号（`select 1` ⏎ `select sleep(2);` ⏎ `select 3;`）。① **前端 `stmtRanges` 换行感知**：`;` 或「下一行以语句关键字开头且不在括号内」都是边界（`STMT_KW`）；但 SELECT/WITH 有歧义（可能是 CTE/`INSERT…SELECT`/`CREATE…AS SELECT`/UNION 的续接），当前累计语句已含续接词（`CONT_KW`=WITH/INSERT/REPLACE/CREATE/UNION/INTERSECT/EXCEPT）时不切——靠**括号深度 + 续接词**判断，多行 SELECT、CTE、子查询、UNION、INSERT…SELECT 全部保持为一条（真机验证 7 例）。box/执行/seqItems 共用这套。② **lint 只 lint 光标所在那条语句**（`runLint` 用 `stmtRangeAtCursor` 取当前语句行区间、错误行号回填原文），不再把整段丢给 sqlglot——因为 `sqlglot.parse` 只按分号拆、会把「换行分隔的多条」当成一条在下一条起始处误报。cursor 移动也重 lint（`onDidChangeCursorPosition`）。③ 后端 `_lint_sql` 保留「整体能解析就放行、否则按空行拆块」作防御层（`_split_blank_line_blocks`，回归 test_lint_blank_line_separated_statements），但实际前端已只送单条。**教训：SQL 语句边界是解析问题，纯文本启发式要靠括号深度 + 续接关键字兜住 CTE/子查询/UNION，别一刀切按换行拆。**
- **长 SELECT 报 2013「Lost connection」的根因与修法（reader 侧，与前面 writer 侧 2013 是姊妹坑）**：reader 的 socket `read_timeout` 原来 = `statement_timeout_s`（30s），而服务端 `max_execution_time` 也 = `statement_timeout_s`（30s）——**二者相等 → 竞态**：长 SELECT 到 30s 时，pymysql 的 socket read_timeout 常抢在 `max_execution_time` 把干净的 3024「超过最大执行时间」错误发回来之前触发，于是报成 2013「Lost connection ... read operation timed out」。修法：reader 的 socket read_timeout 加 `_READ_SOCKET_GRACE_S`（15s）宽限（`engines.mysql_read_timeout`），让服务端 `max_execution_time` 先触发、返回清晰错误；用户调大连接的读取超时（`statement_timeout_s`）时长 SELECT 也能真跑完而不被 socket 误杀。writer 侧无 max_execution_time 约束、socket=write_timeout_s 本身即上限、不加宽限。纯函数回归测试见 test_engines.py（socket read_timeout 必须 > max_execution_time）。
- **MySQL 9.x 的 EXPLAIN FORMAT=JSON 是新 schema（v2.0），字段与旧版完全不同**：旧版是 `{query_block:{table:{table_name,access_type:"ALL",rows_examined_per_scan,filtered,key,cost_info:{query_cost}}}}`；**新版**是 `{query,query_plan:{operation:"Table scan on orders",table_name,access_type:"table",estimated_rows,estimated_total_cost,inputs:[...]}}`——**新版 `access_type:"table"` 才是全表扫描（旧版是 `ALL`）**，行数在 `estimated_rows`、成本在 `estimated_total_cost`、还多了人类可读的 `operation` 串。查询台 EXPLAIN 概览 `walkPlan` 两种都认（`access_type` 小写 `all`||`table` → 全表扫描告警）。**教训：解析 EXPLAIN JSON 别只按旧 MySQL 文档写字段名，真机上先 dump 一次 tree 看实际结构**（这次概览首版按旧格式写，真机 demo-mysql 出来全是新格式字段、access 显示成 "table" 才发现）。
- **查询台多语句顺序执行的做法**（`console.js`）：选中多条一起执行 → `run()` 里 `splitStatements(sql)`（复用 `stmtRanges`，去尾分号）拆成单条，置 `t.seq={list,i}` 后 `run(false,0,parts[0])` 起第一条；带 `sqlOverride` 的递归调用不再进拆分分支。链式推进 `_seqAdvance(t,ok)` 挂在 `pollJob` 的每个终态出口：读/写成功 → `ok=true` 跑下一条，出错/取消/confirm（写需人工确认）→ `ok=false` 停整条序列。每条独立提交 run_async、客户端等前一条 job 终态再发下一条，服务端 (project,connection) 串行不会 Busy 互撞。**数据 tab（双击表名）不参与串行**：run_async 带 `parallel=1` → 服务端 `_solo_key()` 独立 key 并行，不占编辑器查询的连接名额。

- **命令行 AI 省 token（实测 claude input 从 ~25k 降到 ~260，100×）**：`claude -p` 默认加载它自己庞大的 agent 系统提示 + 全局 CLAUDE.md + settings，纯生成 SQL 用不上。三个 flag 砍掉：`--system-prompt "极简一句"`（**替换**掉 agent 系统提示，SQL 规则仍放 `-p` prompt 里）+ `--setting-sources ""`（不加载任何 CLAUDE.md/settings）+ `--disallowedTools "*"`（禁全部工具，安全兜底）。**这些 flag 不影响 `--resume` 会话续接**（实测带着它们 resume 仍记得上文）。codex 侧用 `-c model_reasoning_effort=low`（生成 SQL 低推理档足够、更快更省，实测不掉质量）。**结论：`claude -p` 的大头开销不是 MCP（禁 MCP 只省一部分），是它自己的 agent 系统提示——必须用 `--system-prompt` 覆盖才降得下来。**
- **codex `exec resume` 的两个大坑（追问续接踩出）**：① **别和 claude 共用 cwd**——codex 在 claude 写过 session/上下文的目录里启动会异常变慢直接超时（120s+）；两家 CLI 各用独立稳定目录（`_CLAUDE_CWD` / `_CODEX_CWD`）就正常（首轮 ~8s）。② **`codex exec resume` 子命令的 flag 集比 `codex exec` 小**——**不接受 `--sandbox`**（传了报 `unexpected argument '--sandbox'`），只保留 `--skip-git-repo-check`/`-c`/`-m`/`-o` 等；且 **resume 默认按 cwd 过滤会话**（`--all` 才不过滤），所以首轮和 resume 必须在**同一个** codex 稳定目录才命中会话。修法：首轮 `codex exec --sandbox read-only ... -o f`，续接 `codex exec resume <id> --skip-git-repo-check ... -o f`（去掉 --sandbox），都在 `_CODEX_CWD` 跑。codex 的会话存 CODEX_HOME、`--ephemeral` 会不落盘导致无法 resume，故续接场景不能加 `--ephemeral`。**教训：codex 首轮和续接是两套 flag，改一处忘另一处就静默失败（resume 返回空/0s）。**
- **subprocess 调命令行 AI 必须 `stdin=subprocess.DEVNULL`**（codex 超时的真凶，排查了半天）：手动在终端跑 codex 秒回，但用 `subprocess.run(capture_output=True)` 在守护进程/后台里跑就卡到超时。根因——**codex `exec` 见到「管道 stdin」会把它当 `<stdin>` 输入块等着读**（TTY 下不会），非 TTY 环境继承的 stdin 是个不 EOF 的管道 → 它一直等 → 超时。给 `stdin=DEVNULL`（立即 EOF）即解。claude 无此问题但一并给上无害。**排查特征：手动跑正常、代码里跑必超时 → 优先怀疑 stdin/TTY 差异，不是 cwd 也不是 flag。**
- **launchd 守护进程不继承 shell 环境 → HTTP API 直连报 403（AI 直连 Anthropic/OpenAI 触发）**：`dbm-serve.sh` 由 launchd 拉起，看不到你 zsh 里的 `http_proxy/https_proxy/all_proxy`，进程完全独立。子进程模式（`claude -p` 从开发终端 fork）在 shell 里跑不会撞、走 daemon 就现形。修法**别写死代理到 env 文件**（每换代理都要改），让 `dbm-serve.sh` 启动前 `scutil --proxy` 读 macOS 系统代理注入自己环境（awk 抽 `HTTPSEnable/HTTPSProxy/HTTPSPort` 拼 `HTTPS_PROXY`），系统设置里改完代理 `launchctl kickstart -k gui/$(id -u)/com.db-manage-mcp` 一下就生效；env 文件里显式设置的值仍优先（`[[ -z "${!k-}" ]]` 才导入，作为覆盖入口）。同时 `_run_api` 在 401/403/httpx.HTTPError 分支拼 `_proxy_hint()`——已配代理→提示检查代理连通性，未配→提示可能需要代理，省用户翻文档。**教训：环境类问题（代理/PATH/TZ）默认从系统读，别让用户往配置里手抄；错误消息里主动点出可能的环境根因，比让人肉排查便宜。**
- **接入命令行 AI（`ai.py`）的坑**：① **远程 API 要走代理、别用 NO_PROXY 掐掉**——教训「本机测本地服务绕代理」只对 127.0.0.1 成立；`claude -p` 调的是远程 Anthropic API，`NO_PROXY='*'` 会让它 403「Request not allowed」。子进程默认继承 shell 代理环境即可，别画蛇添足。② **claude `--resume <session_id>` 续接会话必须用稳定 cwd**——会话存档按「项目目录」定位，每次换临时目录 resume 找不到；用固定空目录（`tempfile.gettempdir()/dbm-ai-cwd`，无 CLAUDE.md 省上下文）。③ **禁 MCP 省 token**：`--strict-mcp-config --mcp-config '{"mcpServers":{}}'`（注意是 `{"mcpServers":{}}` 非 `{}`，后者报错），否则加载项目全部 MCP 工具吃 ~25k input token；但 Claude Code 自身 agent 系统提示 + 全局 CLAUDE.md 仍会加载（CLI 模式固有开销，后期 api provider 可消除）。④ **claude 输出 `--output-format json` 取 `result` 字段、`is_error` 判错**；**codex 用 `-o <file>`（`--output-last-message`）直接拿正文免解析 JSONL**，session id 从 stderr `session id:` 正则提，且 resume 需要**不加 `--ephemeral`**（否则会话不落盘无法续）。⑤ **codex 本机 0.131 版本过旧**：默认模型 `gpt-5.6-terra` 要求更新 CLI、ChatGPT 账号又不支持旧模型名 → 真机跑不了，只能等升级。
- **AI 生成物的加工（美化/折行）在拿到返回后用程序做，不塞进 prompt**：① SQL 用 `admin._format_sql`（sqlglot pretty，解析失败原样返回）在路由里美化再回前端——AI 常吐一长条。② 解释「精简、不复述需求」靠 prompt 约束，但**展示不截断（AI 给多少显多少）、折行不切断英文标识符**由前端 `aiWrapComment` 做：按 `/[A-Za-z0-9_.]+|\s|[^\sA-Za-z0-9_.]/` 切成单元（ASCII 词/标识符整体保留、中文逐字），只在单元间断行 → `user_id`/`idx_orders_created`/`LIMIT` 不会被拦腰截断，中文自由折行。**教训：这几项需求用户明确要「程序做」而非「prompt 做」，别偷懒写进提示词。**
- **AI 浮层交互**：查询台是「少弹框/一屏」风格，AI 面板别用挤占编辑区的 in-flow 大块（第一版做成 `dg-drop` 把编辑器顶下去、被用户否掉）。正解：**编辑器右上角浮按钮（对齐 schema 选择器、放其左侧留间隔）+ 可全屏拖动的 `position:fixed` 浮层小卡片**（fixed 才能拖出编辑区到结果面板上方；祖先无 transform 时 fixed 相对视口，本项目 `.dg-editor/.dg-main/.dg-root` 均无 transform 故安全）。插入用 `editor.executeEdits` 在光标处（非合成打字），追问「替换上一条」靠 track 上次插入的 Monaco Range。

- **通知/邮件/短信等"发出即真实生效"的副作用：默认必须 no-op，渠道由入口决定不由默认值决定**（本次踩坑）——`DbmService.__init__` 第一版把 `notifier` 默认改成 `build_default_notifier()`（macOS 上就是真的 osascript），跑一次 `pytest tests/test_approvals.py` 就在系统通知中心里连弹 9+ 条「新审批单 #1 · demo/main」。原因：`test_approvals.py::TestHappyPath` 等用例走完整 execute → `_request_approval` → notifier.send() 的路径，走的是真 notifier。修法：**服务层构造函数默认 `NoopNotifier`**，只有真 daemon 入口 `_cmd_serve` 才注入 `build_default_notifier()`。**教训：任何"离开进程边界"的副作用（本地通知、邮件、Webhook、短信、写第三方 API）在库/服务层的默认值必须是 no-op**，测试与库集成路径永远不产生真副作用；渠道由 CLI/daemon 入口决定，而不是让默认值自动激活最"用户友好"的实现。排查特征：只有跑测试时才有的重复通知/邮件 → 优先检查该组件的默认构造是否偷偷起了真实副作用。
- **长阻塞的 MCP 工具（审批等待）的三个坑**：① **等待要用异步轮询，别用进程内条件变量**——决策可能来自另一个进程（`dbm approve` CLI），条件变量唤不到；1s 一次的 `anyio.sleep` + 短 SQLite 读对「人点批准」完全无感，且天然跨进程。② **不能占线程池**：等待期间只在每次复查时借一下 `to_thread` 跑 SQLite 读，绝不能把整个等待丢进 `to_thread`（会吃掉 `mcp_max_concurrency` 的名额，几个挂起审批就把并发打满），更不能在事件循环里同步 sleep——**人正是要在同一进程的管理后台上点批准，等待期间后台必须照常响应**（e2e 里专门断言了等待期间 GET/POST /admin/approvals 正常）。③ **给长调用发 `ctx.report_progress` 心跳**（每 10s），客户端不支持就吞掉异常；客户端单次工具调用超时更短时靠「超时返回 pending + 再调一次续等」兜底，不会丢单。**另：把默认行为从「立即返回」改成「阻塞等待」会让既有测试直接挂住**（test_elicitation 断言 `approval_required` 的两个用例要显式传 `wait_seconds=0`）——改默认值前先想清楚哪些测试依赖旧的立即返回。
- **连接健康位 + 后台重连 + ConnectionUnavailable 明确回传给 agent**（`health.py`）：
  - `HealthMonitor` 按 `(project, connection)` 合并跟踪（不分 reader/writer——共用同一网络路径，分开跟踪收益小复杂度高），三态 `ok`/`unavailable`/`exhausted`；退避 5→15→30→45→60s（封顶后持续重试，不放弃），连续 5 次失败标 exhausted；`_run_touching_db` 包所有会触达 DB/隧道的入口（`_read`/`admin_run_sql` 写分支/`_execute_approved`/`admin_import_rows`/Redis 读写命令 + 所有走 `_audited` 的方法）——入口 `health.check()`、成功 `mark_ok`、失败按 `is_connection_error` 分类打标 + 顺手 `pool.dispose_connection`；连接配置变更走 `force_clear`。
  - **`is_connection_error` 类名匹配的两个坑**：① `OperationalError` 在 pymysql=连接断，但**在 sqlite/sqlalchemy 也覆盖"no such table"、"syntax error"等业务错**——仅按类名判定会把 SQL 错也当连接错，进而给业务错触发重连；把 `OperationalError`/`DBAPIError` 放到 `_AMBIGUOUS_EXC_NAMES`，**必须叠加连接级消息片段**（`lost connection`/`gone away`/`connection refused` 等）才判连接级。② `ConnectionError` 是 Python 内建（socket 层），归为严格连接级；redis-py 的 `ConnectionError` 类同名但走继承链一样命中。
  - **异步重连线程的两个坑**：① 单元测试要用 monkeypatch 把 `BACKOFF_STEPS_S` 压到 `(0.01, 0.01, 0.01)`，别指望在 5 秒内推进真实 5→15→30→45→60 阶梯；只推进 `next_retry_at` 提前不够——线程仍在 `time.sleep(wait)` 里睡。② `Health._thread` 存 Thread 引用，daemon=True，`monitor.stop()` 只需要 `self._closed = True` + 清 entries，各循环下一轮就自然退出。
  - **agent 回传**：`server.py::_tool_error_from_unavailable` 把 `ConnectionUnavailable` 转成带前缀标签的 ToolError（`[connection_unavailable]`/`[connection_exhausted]`），agent 一眼分辨"稍后重试"vs"要人介入"；文案带建议重试秒数与最近错误摘要，不再是 pymysql 2013 原样。
  - **exhausted 时发一条通知**（人为介入信号）；`HealthMonitor` 内部只在从 unavailable→exhausted 那一次转变时调 `on_exhausted`，天然去重、不轰炸。
  - **人工重连入口（`service.reconnect_connection` + `/admin/sql/reconnect`）**：连接一旦 exhausted，后台退避线程已放弃、`health.check()` 又会挡下所有触达 DB 的动作——**连 `test_connection` 都自愈不了**（它走 `_run_touching_db → health.check()`，exhausted 直接抛 ConnectionUnavailable，根本不尝试重建）。所以必须有一个**绕过健康位**的专用重连：`force_clear` 清状态 → `_health_probe`（先 dispose 旧引擎/隧道，再用全新连接跑 SELECT 1 / PING）；成功即恢复，仍失败则记审计 + `mark_failed` 重新进入后台退避。查询台把它挂在**左树「库/连接」节点的右键菜单**（`console.js` `openDbCtx`/`reconnect`，库节点与绑定库连接的 `tables` 根节点都挂 `@contextmenu`）——不是错误横幅按钮（用户明确要放右键菜单）。**教训：健康位是"入口守卫"，任何要在 unavailable/exhausted 下仍能执行的自愈动作（重连/改配置）都必须显式绕过 `health.check()`，不能复用普通 DB 触达路径。**

- **给看板画图，稀疏序列必须补成完整时间窗**：SQL 按小时 `GROUP BY` 出来的只有「有数据的那几个小时」，一小时窗口里只有一个桶时，柱子宽度 = 整幅宽度，渲染出来是一整块实心色块，既不像图表也看不出其余时间其实是空闲的。正解是前端按 `generated_at` 与窗口长度**补齐空桶**（`fillSeries`）。另外粒度要跟着窗口走——一律按小时的话，1 小时窗口只剩一两个点、30 天窗口有 720 根柱子；改成 ≤1h 用分钟、≤48h 用小时、更长用天（`traffic_series` 的桶宽就是 UTC ISO 前缀长度：10/13/16）。
- **给 agent 的「用法说明」不能只放 MCP instructions**：各客户端对 instructions 的处理差异很大（截断、折叠、只在最外层放一次），实测 agent 读不到或读过就忘。可靠的送达点是**会话第一次成功调用工具时**——用 fastmcp 的 `Middleware.on_call_tool` 给 `ToolResult.content` **前插一个 TextContent 块**（不动 `structured_content`，按 schema 消费的客户端完全无感），会话 id 去重、有界 FIFO 存已发过的会话。只在**成功**的调用后记账：首次调用就报错时把一大段说明拼在错误前面，反而会盖住「下一步该怎么办」。
- **单次结果上限管不住「一直查」**：行数 + 字符预算都是**每次调用**的闸门，一次 1 万字符查两百次照样烧掉几十万 token（多半还是 agent 陷进了重拉同一份数据的循环）。补一道**会话级**配额（`budget.py`）：累计超限就拒绝取数，错误文案是「**停下来问用户**是否确认继续」而不是「换个写法重试」，用户点头后 agent 调 `allow_more_results(reason=...)` 才追加一份额度——额度不自动续、放行理由留痕并显示在看板上，人能核对它到底问没问过。追加时用 `max(allowance, used) + limit`，不能从 0 重算，否则超得越多反而赚得越多。

- **看板的图表用 echarts、别自己画 SVG（真实反馈：「操作数那个图表要有 Tooltip」）**：第一版手绘 `<rect>` 柱图能显示形状，但 hover tooltip、坐标轴刻度、图例这些「看板真正要回答的问题」（那根柱子是几点？多少次？其中失败几次？）全都给不了，自己补等于重写半个图表库。`static/echarts.min.js` 早就 vendored 了（查询台图表在用），直接复用。两个坑：① echarts 是 **UMD**，`<script>` 必须**同步**加载且早于用它的脚本（本页不加载 Monaco 所以没有 AMD 冲突，但顺序仍要对，否则 `window.echarts` 是 undefined）；② 容器必须有**确定高度**，`echarts.init` 时量到 0 高就什么都不画——CSS 里给 `#dash-chart-*{height:170px}`。实例只 `init` 一次、之后 `setOption` 更新：每 5s 重建会闪，也会漏 dispose。**堆叠系列必须是能相加的分解**——「成功/失败」相加等于总数，而「写操作」与「失败」会重叠，硬堆起来的柱子高度就不再是总次数了，所以写操作只放进 tooltip 文案。

- **设置页开关的值必须由隐藏 input 承载**：`<input type=checkbox>` 未勾选时**根本不会进 FormData**，而保存接口要的是显式的 `"true"/"false"`。做法是复选框本身**不带 name**（只带 `data-field`），同名隐藏 input 存值，JS 在 toggle 时改隐藏 input。用「hidden false + checkbox true」两个同名字段的老套路不行——勾选时 FormData 里会有两个值，`form.get(key)` 取到的是第一个（false）。
- **脏值追踪要按「存取器」建模，别直接拿 DOM 元素比**：① **单选组必须按组算**——radio 的 `.value` 从来不变，按元素比根本检测不到改动；而且切一次渠道会被数成两处改动（一个取消选中、一个选中）。正解是每个 name 一个存取器，读 `form.elements[name].value`。② **「放弃」是程序赋值，不会自己触发事件**，而页面上好几处联动都挂在 `change`/`input` 上（通知渠道字段显隐、AI 后端显隐、数字换算读数）——每个 write 都要补发一次事件，否则值回去了、界面还停在原样。
- **JS 里 `const` 的 TDZ 会让整个 IIFE 静默死掉**：设置页第一版把「开关初始化」写在了「脏值追踪声明」之前，开关的 `sync()` 里调 `dirtyCheck()` → `changedFields()` → 访问尚未初始化的 `const fields` → 抛 ReferenceError → 整个立即执行函数当场终止。**表现极具迷惑性**：第一个开关的文字设上了（抛错前那一行）、后面的开关和所有换算读数都没出来，而且错误发生在页面加载时、控制台事后打开根本看不到。**排查特征：脚本「做了一半」——前面几行的效果在、后面的全没有 → 一定是中途抛了错，去看声明顺序而不是去看逻辑。**
- **`:has()` 写的定宽会把整宽行一起管住**：给 `.ctl` 加 `width:240px` 之后，本该占满一行的「整宽行」（提示词文本框、通知渠道卡片、webhook 输入）全被压成一条 240px，中文折成「只在后台/铃铛里」这种断法。定宽必须在整宽变体里显式撤掉（`width:auto`），别指望 `justify-self:stretch` 能覆盖 `width`。

- **重设计一个表单页时，真正要锁住的不是版式而是「接口面」**：保存路由读的每个 `name`、前端按条件显隐用的每个 class 钩子、JS 取的每个元素 id。版式可以随便推倒重来，这三样丢一个就是静默失效（字段保存不上、某引擎该隐藏的行露出来、按钮没反应）。做法是把它们各列成一张表写成回归测试（见 test_settings_page.py::TestConnectionsTab），改版时先跑这三条。

- **看板把「被挡下」当成「失败」是实质性误报**（自查时发现）：agent 每提交一次写操作都会先落一条 `status=rejected` 的审计记录（生成审批单、没落库），那是审批流的**正常一步**。而看板的「失败」原本算的是 `rejected + error`，于是审批流跑得越顺，看板上的红色越多。修法：`traffic_series` 分别返回 `rejected` / `errors`，磁贴写成「写 N · 被挡下 N · 出错 N」且只有 error 才标警示色，图表改成三段堆叠（成功/被挡下/出错，相加仍等于总操作数）。**教训：把「状态 != ok」笼统当失败，在一个「拒绝是正常路径」的系统里必然误报。**
- **token 计数：装了 tiktoken 就别再估**（实测数据说话）：对本服务最常见的内容——查询结果 TSV——字符类别启发式**少报 49%**（一份 43KB 结果真实 16131 token，估出 8000 上下）。原因是制表符、纯数字 id、短字段各自成 token，密度远高于「4 字符/token」。改法：可选依赖 `tokenizer`（tiktoken，o200k_base），43KB 编码 1.5ms；**词表 3.4MB 首次加载会下载**，所以 ① 缓存目录钉到数据目录（默认在 TMPDIR，被 macOS 清理后又要重下），② serve 启动时在 daemon 线程预热（别让某一次查询替所有人承担这几秒），③ 装不上/下不到就**永久回退**启发式（记住失败、不每次重试）并在界面标「≈粗估」。o200k 是 GPT-4o 的分词器不是 Claude 的，但同为现代 BPE、中文处理正确，比启发式接近得多。**教训：给「这值多少上下文」这种数字，先量一遍你实际的内容类型再选算法——通用文本的经验值对 TSV 完全不成立。**
- **token 数是估算，字符数才是闸门**：配额以**字符**为单位强制（确定、可复现、不依赖任何分词器），token 只是给人看的注解。原来用一个固定除数 3.5 换算，但真实密度差三倍——纯英文约 4 字符/token，纯中文约 1.2，同样 40 万字符英文约 10 万 token、中文能到 33 万。改法：`budget.estimate_tokens(text)` 按字符类别（ASCII / 非 ASCII）分别估，`charge()` 收**原文**而不是长度；设置页只有上限没有原文，仍用固定除数但标明「粗估」。要精确只能调厂商分词器/计数接口，为在结果末尾显示一行提示去做网络调用不划算。
- **`COUNT(DISTINCT session_id)` 会把空串算成一个会话**：查询台自身的操作 `session_id=''`，于是「N 个会话」恒多一个。用 `COUNT(DISTINCT NULLIF(session_id,''))`。
- **SQLAlchemy 的 SQLite 池按 database 分两种**：文件库用 `QueuePool`（有 `checkedout()`），`:memory:` 用 `SingletonThreadPool`（没有）。看板对取不到的指标要显示「—」而不是 0——「这类池不报这个数」和「没占用连接」是两回事。
- **看板的「及时性」有一条固有边界**：`audit_log` 是操作**结束后**才落库的，所以正在跑的查询不计入「操作数/流量/配额」，只出现在「此刻正在执行」里（那份是进程内的在途登记簿）。实测一条 22 秒的查询：执行期间 live=1、ops 不变、配额 0；结束后 live=0、ops+1、配额记上。这是设计使然，不是延迟。

- **PG 连一个不存在的库，会被健康检查当成断连**（做 PG 跨库时发现的潜伏 bug）：psycopg 的原文是 `connection to server at … failed: FATAL: database "x" does not exist`，正好命中 `health._CONNECTION_LEVEL_MSG_PARTS` 里的 `"connection to server"` → **整条连接**被标 unavailable、连累其它库上的查询。修两道：`is_connection_error` 对 3D000 / `database "…" does not exist` 显式返回 False；agent 传入的 `pg_database` 在建连接**之前**先对照 `pg_database` 清单校验（`service.resolve_pg_database`，60s 缓存）。**教训：凡是「由外部输入决定连到哪」的参数，都要在碰连接池之前校验，否则一个拼错的名字能打坏共享的健康位。**
- **注释说「持久化」不等于真的持久化**：`console.js` 里 `pgDbSel` 的注释一直写着「（持久化）」，实际 `persist()`/`restore()` 从没存过它；tab 的 `db` 也没存。以前没暴露，是因为加载时左树会把所有 tab 的库统一改写；改成每 tab 独立后，刷新页面就会让 tab 悄悄回到默认库执行——浏览器 e2e 里专门做了「刷新后再跑一次 `SELECT current_database()`」才发现。**加新的 tab 级状态时，同时检查 persist 与 restore 两处的字段清单。**

- **多语句顺序执行遇到写确认会死循环（真实反馈：生产环境 ALTER + COMMENT 两条一起执行，确认框反复弹、两条都没执行）**：序列在第一条写上停下等确认时，`_seqAdvance(t, false)` 直接把序列清掉；点「确认执行」走的 `run(true)` 又因为**选区还在**重新进了多语句拆分分支，从第一条重新开始、confirm 标志也丢了——于是第一条永远在要确认，一条都执行不到。修法：确认时不进拆分分支；需要确认的写只把序列标成 `awaitConfirm` 暂停，确认后由那次执行的结果接着推进；取消确认或中途执行别的语句都会放弃序列。**教训：「暂停等人」和「失败中止」是两种状态，别共用一个出口；带选区的编辑器里，任何「再调一次 run」都要想清楚会不会重新进选区分支。**
- **选中多条执行只确认一次**（真实反馈「不管实际是几条，都应该只需要确认一次」）：执行前先 `POST /admin/sql/assess_batch`（`service.admin_assess_batch`）整批只分类不执行——有语法错整批不跑；全只读直接跑；含写返回每条写的风险与**各自的指纹**，前端弹一次确认，之后逐条带 `confirm=1` + 这一条的指纹执行，H1 指纹绑定逐条仍然生效（确认后改过的 SQL 会被拒）。只有一条写时才取执行计划。旧的「逐条暂停等确认」(`awaitConfirm`) 保留为兜底。**另：浏览器存档里的 PG 库可能已不存在**（被删/改名/换配置，左树缓存里的库清单也是旧的）——命中缓存后后台重拉一次库清单（`recheckPgDbs`），指向已不存在库的 tab 一律归到左树当前库；这是 e2e 时新容器没有旧库、所有语句都报「database does not exist」暴露的。
- **`COMMENT ON` 是低风险**（据反馈）：sqlglot 把它解析成独立的 `exp.Comment`，`risk._assess_one` 原来没有这一支，落进「无法识别 → CRITICAL」。现归为 LOW（只改注释、不动数据）；风险等级只影响展示，`requires_approval` 仍恒为 True，写操作照样要确认/审批。顺带：PG 合法的 `COMMENT ON … IS NULL`（清除注释）sqlglot 解析不了（只认字符串字面量），`normalize_sql_for_parse` 对 postgres 把它临时换成 `IS ''` 供解析，执行仍用原文（真机验证注释确被清空）——与 MySQL DROP PARTITION 同一套「解析归一 ≠ 执行改写」做法。
- **写确认框慢，大头是给 DDL 取执行计划**：确认前 `_try_explain` 先用 reader 再用 writer 跑 `EXPLAIN <SQL>`，而 DDL / COMMENT / GRANT 根本不能 EXPLAIN、两次必然都失败——远程生产库上 writer 连接常被空闲回收，为一次注定失败的 EXPLAIN 重建连接（可能还要过 SSH 隧道）就是那几秒。修法：`engines.explainable()` 只放行单条 DML / 查询。前端轮询任务结果也从固定 400ms 改成前一秒 100ms（写确认本身只要几十毫秒）。**风险评估取元数据要带 schema**（后续已修）：`risk._assess_one` 原先只把裸表名交给 provider，`console.ev` 这类会到默认 schema 里找、永远查不到（风险报告没有行数/索引，每次确认还重新反射）。现在 provider 收到的是 `schema.表`（展示仍用表名），查询台的执行 schema 作为未限定表名的默认值；`estimate_row_count` 四种库都支持 schema——**PG 还必须 join `pg_namespace`**，原来只按 `relname` 查，不同 schema 下的同名表会取错。真实 PG17 / MySQL 8.4 验证见 `tests/test_meta_schema.py`。
- **给已有存档加新字段时，「缺字段」不能当成一个合法取值**（PG 跨库上线后真实反馈：表视图报「relation … does not exist」）：tab 的 `db` 字段是新加的，升级前的存档里没有，而「上次选的库」(`pgDbSel`) 以前也没真正存过 → 恢复出来 `db=""`，被当成「连接默认库」执行，而左树显示的是另一个库。以前左树加载时会把所有 tab 统一改写，恰好掩盖了这个问题。修法 `adoptPgDb`：PG 下 `db` 为空的 tab 一律归到左树当前的库；新 tab 直接取左树正在显示的库。复现要点：**要在不加载查询台的页面上改 localStorage**，否则离开查询台时的自动保存会把改好的旧存档覆盖掉，测了个寂寞。查询出错时审计 detail 现在保留 `db=` 前缀（原来被错误信息覆盖，排查时看不出在哪个库上跑的）。

- **引擎特有行为收进可插拔驱动，别再散落 if engine == 清单**（用户要求「后续加 DB 支持就加驱动，驱动可以自己写、也可以用成熟驱动库」）：原来 engines.py 有十几处 `engine_kind ==` 分支，admin/sync/probe/service 各自还藏着引擎清单（表单下拉、默认端口、图标、lint 方言、同步源目标、AI 支持…），加一个引擎要改十几个地方、还必然漏。修法：`drivers/base.py::DbDriver`（所有方法都有能用的默认实现：取消=no-op、容量/行数=空、DDL=反射拼近似、语法复核=不支持，缺的能力**优雅降级**而不是报错）+ `DRIVERS` 注册表（`register()` 传类即实例化）+ 5 个内置驱动；engines.py 的引擎分支全部改成 `get_driver(kind).xxx(...)` 委托，1215→819 行。**三个关键收口**：① `config.Engine` 从 Literal 放宽为 **str**——配置层不再校验引擎清单，建连时 `get_driver` 找不到才报「未注册」并提示怎么加（这是「加驱动不用改别处」的最后一环，否则新引擎的配置校验过不了）；② 清单全部改成**运行时从注册表算**（`connectable_engines()`/`sync.source_engines()`/表单下拉/端口 JS），**不能算成模块级常量**——晚注册的驱动（测试替身、未来插件式加载）会看不到；③ 能力是驱动属性（`has_schema_layer`/`sync_target`/`ai_sql`），默认值必须等于旧行为（sqlite 无 schema 层、ClickHouse 本项目只读不做同步目标、AI 生成按方言覆盖度开关）。**重构中踩的三个坑**：（a）sqlite 驱动的 `explain_prefix` 必须是 `EXPLAIN `（审批流看 VDBE opcode 表，列是 addr/opcode），`EXPLAIN QUERY PLAN` 是**查询台另一个入口**（列是 id/parent）——两个前缀别混，驱动里同时存 `explain_prefix`/`explain_json_prefix`；（b）驱动的 `get_table_ddl` 要先 `_ensure_table_exists` 再查 sqlite_master/SHOW CREATE TABLE，否则缺表返回空串不报错——批量 DDL 的「一个坏表名如实标出来、不废整批」依赖这个 ValueError；（c）未知引擎在语法复核路径必须**降级为 `SyntaxCheck(supported=False)`** 而不是抛 `UnsupportedEngineError`（后者会让 agent 的 execute 拿 500，违反「默认拒绝」红线——`_syntax_check_supported`/`_check_one_statement` 包一层 try）。**教训：清单型 if/elif 每多一处，「加引擎」就多一个必须人工记起的改点；能注册表化的就别留清单，清单实在消不掉的（privileges/checkup 的专属 SQL）要在模块地图里写明「这里加引擎需要另写 SQL」。**

- **导出改造：不截断 + 异步 + 进度弹框（真实反馈三轮）**：
  - **① 导出必须走独立上限，不能被查询台的 `max_rows` 截断**：原来 `admin_export` 用 `cfg.policy.max_rows`（默认 500/1000）注入 LIMIT，导出根本拿不到完整结果集。新增系统设置 `export_max_rows`（默认 100 万，区间 100–2000 万），查询台分页用小 `max_rows`、导出用大上限，两者解耦。**仍保留上限不是不设**：序列化缓冲在内存里，无上限会把进程拖垮；超过上限时 `truncated` 如实标注。截断探测沿用 `paginate_sql(sql, engine, limit+1, 0)` 多取一行：stream_rows 最多 yield `limit+1` 行，消费方把第 `limit+1` 行只当存在标记、不写盘——恰好等于上限不算截断。
  - **② 大结果导出必须流式，逐单元格算体积会慢 40 倍**：百万行导出实测 125s → 3s，瓶颈是 `estimate_cell_bytes` 逐单元格调用（百万行×列数的 Python 函数开销）。改成每行只采样首个单元格 + 其余按固定 16B 估——审计统计只要量级，不必精确。另：`engines.stream_rows` 每批 `fetchmany(_STREAM_BATCH=2000)` 逐批 yield，内存只占一批；`export.stream_export` 的 writer 逐行写缓冲，CSV/JSON/Markdown 三种格式的流式输出已做到与原 `to_*` 函数**逐字节一致**（回归测试对拍，含反斜杠/管道符/换行转义）。
  - **③ 异步任务进度回传链路有「断点」**：JobManager 加 `progress` 字段 + `report(value)` 回调只是前半段——**路由 `/admin/sql/job` 组装响应时漏了把 `snap["progress"]` 放进 JSON**，前端永远收到 null。这种「中间层有、接口没透」的断点只能靠真实跑一遍异步任务发现，单测里 mock 不到。排查特征：curl 轮询 job，running 时 `progress` 一直 None 但任务确在耗 CPU。
  - **④ 弹框交互**：`exportAs` 提交 `/admin/sql/export_async` → 打开 `.dg-exp` 弹框（复用体检浮层的视觉语言）→ `pollExport` 轮询（300ms，客户端秒表锚定服务端 `elapsed_ms`，与 `pollJob` 同一套）→ 完成时弹框开着就直接下载、关掉了就 `flash()` toast（铃铛未读数由后端 `notifier.send` 写收件箱 + SSE 自动 +1）。**关掉弹框只置 `closed=true`，轮询不停**——这是「关掉弹框异步继续导出」的关键。取消复用 `/admin/sql/cancel`（KILL QUERY）。
  - **⑤ 文件落服务端而非塞进 job 快照**：导出结果经 `_save_mcp_export` 写 `data_dir/mcp_exports/<token>/`（0700，TTL 1 小时），job 只存 token + `download_url` + 摘要。百万行 84MB 的 blob 进任务快照会被轮询接口反复序列化。
  - **验证方式**：后端链路（提交→进度→完成→token 下载→通知）用 curl 对测试服务（8211 + 临时数据目录）完整跑通；真实 MySQL e2e 6000 行（超过连接 max_rows=200 不截断、4 次进度回调、写 SQL 被拒）；前端 JS 用 `node --check` 校验语法 + 确认模板引用的方法全在 `methods` 里声明（Vue 模板取不到方法会白屏）。**浏览器自动化（Playwright MCP）中途 Transport closed 不可恢复**——多个 playwright-mcp 进程实例冲突、pkill 后 npm exec 不再自动拉起；改用 CDP 直驱 Chrome 也卡在 Vue 生产构建剥离 `__vueParentComponent`。结论：**后端接口链路用 curl 验最稳，前端语法/绑定用静态检查兜住，浏览器 e2e 留给人工或后续修复 MCP 通道**。
